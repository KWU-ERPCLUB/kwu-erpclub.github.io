- 같은 피싱 표본에서 질문을 하나로 던지면 62.6%, 신호 다섯 개로 쪼개면 95.0%였다(beri 독립 실측).
- 값은 입력 100만 토큰당 $0.042, 출력 과금 없음. 채점 100만 건으로 환산해 $160이라는 기록이 있다.
- 나한테 왜: 라벨링 값이 내려가는 대신 정답 세트를 만드는 일이 병목으로 남는다.
:::

먼저 돌려본 기록들에서 정확도와 값은 실제로 어떻게 나왔나

## 무슨 일

TypeSafe AI가 9월 15일 Jev를 공개했다. 글을 쓰지 않는 모델이다.

회사는 이 계열을 시스템 원(System One) 모델이라고 부른다.

입력은 평가할 대상과 질문 묶음이다. 출력은 문장이 아니라 정해진 타입의 값과 확률이다.

글을 못 쓰는 것은 결함이 아니라 설계다. 요약도 코드도 판단 이유도 못 쓴다.

대신 스키마 밖의 값은 나올 수 없다.

## 실물: 무엇을 주고 무엇을 받나

공식 문서 기준 질문은 세 종류다.

| 질문 | 형식 | 돌려주는 것 |
|---|---|---|
| Choice | 보기 중 하나 선택(최대 255개) | 고른 값과 보기별 확률 |
| Score | 척도 위 위치(최대 10단계) | 확률 가중 평균값 |
| Noul | 참·거짓 | 참일 확률 |

같은 대상에 질문을 여러 개 붙여도 한 번에 답한다. 응답은 70~500ms다.

컨텍스트는 32,000 토큰이다. 값은 입력 100만 토큰당 $0.042이고 출력 과금이 없다.

접근 경로는 아직 좁다. 직접 API는 대기 명단 방식이고 무료 등급이 없다.

Vercel AI Gateway를 경유해 부르는 방법이 공식 안내에 있다.

필자는 9월 20일 Cloudflare 경로로 호출해 봤다. 결제 수단이 없어 402(결제 필요)가 돌아왔다.

::: 용어
시스템 원(System One) | 사람의 빠른 직관적 판단에서 따온 이름. 과정을 풀어 쓰지 않고 판정만 내놓는 모델 계열을 가리킨다
Noul | 참·거짓에 확률을 매기는 질문 형식의 이름
로지스틱 회귀 | 여러 신호를 하나의 확률로 합치는 통계 기법. 신호마다 가중치를 학습한다
보정 | 모델이 붙인 확률이 실제 적중률과 맞아떨어지는 정도. 0.9라고 한 건들이 실제로 90% 맞으면 잘 보정된 것이다
:::

## 앞선 사례: 먼저 돌려본 기록들

성능은 모델이 아니라 질문 설계에서 갈렸다.

기술 매체 beri가 피싱 메일 2,000건으로 독립 실측을 했다. 본문은 합성 데이터다.

정답 라벨은 URL 평판 데이터로 붙였다고 밝혔다.

"이것이 피싱인가"를 한 질문으로 던지니 62.6%였다. 같은 표본에서 Claude Haiku는 81.3%였다고 한다.

다음이 갈린다. 같은 모델, 같은 표본에서 질문만 바꿨다.

신호 다섯 개로 쪼갰다. 단축 URL 사용 여부, 조직 사칭 여부 같은 것들이다.

1,000건으로 가중치를 로지스틱 회귀로 학습했다. 나머지 1,000건에서 95.0%가 나왔다.

같은 조건에서 Haiku는 93.2%였다. 정규표현식 기준선은 91.8%였다는 보고다.

해당 분석은 95%를 모델 혼자의 성과로 보지 않는다. "Jev와 라벨과 회귀의 조합"으로 적었다.

확률 자체가 쓸모인 구간도 있다. 평가 도구 업체 Arize의 스팸 분류 기록이다.

0.1 미만으로 매긴 메일 중 실제 스팸은 0.1%였다. 0.9 이상 중에서는 99.9%가 스팸이었다.

임계값으로 자동과 수동을 가르자 사람이 볼 몫은 4.6%로 줄었다.

라벨 없이 잰 정확도는 98.3%였다. 라벨 14,800건으로 훈련한 기존 통계 모델은 98.4%였다.

값 차이는 더 크다. Langfuse가 인용한 Good Start Labs 벤치마크가 있다.

채점 6,003건을 100만 건으로 환산한 값이다. Jev는 $160이었다.

Gemini 3.8 Flash는 $1,600이었다. Claude Fable 5.1은 $33,000이었다.

## 판정 기준: 어디에 걸리고 어디에 안 걸리나

걸리는 조건은 하나다. 답의 보기를 미리 다 적을 수 있는 질문인가.

금융에서 거론되는 자리는 둘이다.

하나는 청구서 검증이다. 인보이스를 발주서·계약·과거 청구와 대조한다.

중복 청구나 거래처 오기 같은 사기 신호를 판정하는 용도다.

다른 하나는 조사 순서다. 거래 적요와 KYC(고객 확인) 자료로 자금세탁 의심 건을 줄 세운다.

금액 계산은 코드가 맡는다. 모델은 의미 판단만 맡는 구성으로 소개된다.

마케팅은 양이 문제라 값이 곧바로 효과를 낸다.

DataCamp 설명에는 5,000만 행 리뷰 테이블이 예로 나온다. 감성과 정책 위반을 전부 매겨도 약 $20 수준이다.

개발자 Flavio Copes의 기록도 있다. 목록 98,000건을 10분에 분류하고 약 $0.02를 썼다.

분류 말고도 쓰임이 거론된다. 검색어를 정보형·비교형·구매형으로 나누는 의도 분류다.

고객 피드백을 항목별로 갈라 담당 팀에 넘기는 라우팅도 같은 꼴이다.

안 걸리는 자리도 분명하다. "이 카피가 좋은가" 같은 모호한 평가와 순위 예측이다.

이유를 문장으로 남겨야 하는 업무도 밖이다. 거절 사유를 설명해야 하는 금융 심사가 그렇다.

## 확인 안 된 것

| 항목 | 상태 |
|---|---|
| 한국어·비영어 성능 | 공식 문서·소개 자료·독립 실측 어디에도 수치 없음 |
| 벤더 자체 4개 업무 평균 67.8% | 사람이 붙인 정답이 아니라 더 큰 모델들의 예측과 얼마나 일치하는지로 잰 값 |
| "모르겠음" 처리 | 보기를 주면 반드시 하나를 고른다. 형식 오류가 없다는 뜻이지 답이 맞다는 뜻은 아니다 |
| 국내 금융 업무망 반입 | 전자금융감독규정 개정으로 평가 "충족" 등급 SaaS만 내부 업무 허용, 신용정보 처리는 제외 |

## SO WHAT

**첫째, 값이 내려간 자리에 라벨 작업이 남는다.** 62.6%를 95.0%로 올린 것은 모델 교체가 아니었다.

질문 분해와 라벨 1,000건이었다. 모델 호출이 싸져도 정답 세트를 만드는 일은 그대로다.

**둘째, 질문 설계가 성능 변수다.** 큰 질문 하나를 신호 여러 개로 쪼개는 방식이다.

이 방식은 Jev 없이 기존 모델에도 그대로 적용된다.

지금 쓰는 분류 프롬프트가 한 줄짜리 질문이라고 하자. 그 한 줄이 성능 상한일 수 있다.

**셋째, 확률을 구간으로 쓰는 감각이 실무 쪽이다.** 정확도 한 숫자보다 쓰임이 많다.

0.9 이상과 0.1 미만을 자동으로 돌렸을 때를 기준으로 잡는다. 남는 검토량이 몇 퍼센트인지가 실제로 쓰는 값이다.

한국어 성능은 이 글을 쓰는 시점에 공개 자료가 없다. 쓸지 말지는 직접 재 본 뒤에 판단할 일이다.
